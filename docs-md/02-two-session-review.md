# 一份 Dataset 写完初稿之后, 怎么审

这份文档描述的规则, 由 [.claude/skills/review-fake-data-generator](../.claude/skills/review-fake-data-generator/SKILL.md) 这个 Skill 具体实现, 修复这一侧则复用 [.claude/skills/fake-data-generator](../.claude/skills/fake-data-generator/SKILL.md) 本身. 这里只讲 review 这一侧的机制是什么, 为什么要这么设计. 怎么把 review 和 fix 自动串成一个无人值守的循环, 是下一篇文档的内容, 这里不展开.

## 1. 为什么这一步必须交给 AI

按照 [01-dataset-anatomy.md](01-dataset-anatomy.md) 里定的规矩写完一份初稿之后, 没有人能一步到位. 人能审的东西是有限的: project framing 有没有选对, 这个虚构公司的 background 站不站得住, 业务问题挑得对不对, 这些方向性的判断人做得来, 而且应该由人做. 但再往下一层, 比如某个 SQL 查询里引用的字段是不是真的存在于 ER 文档声明的表里, 生成脚本里某个分布的参数是不是真的对应业务背景文件里写下的那个百分比, 几十个字段的命名在四份文件里有没有全部对齐, 这些细节的比例和一致性问题, 人类审不过来, 也不该指望人类审得过来. 这正是这一步必须交给 AI 的原因: 不是因为人不够聪明, 而是因为这类工作的体量和粒度天然超出人工审核的可持续范围.

---

## 2. review 是查一致性, 不是挑战业务设定

review 的边界很关键, 必须说清楚. review 不 challenge 业务设定本身, 也就是说不去质疑这个虚构公司该不该存在, 这个 project framing 选得好不好, 这个业务问题提得对不对. 业务背景, ER 文档, SQL 查询题, 生成脚本, 这四份文件里作者已经定下来的业务判断, 是 review 阶段的既定事实, 不重新协商.

review 真正要 challenge 的, 是这份业务设定有没有被前后一致, 没有漏洞地兑现出来. 具体查两类东西: 第一, 四份文件之间是否自相矛盾, 业务背景说的 business problem, ER 文档有没有对应的字段和关系撑住它, SQL 查询题有没有真的在回答它, 三者对不上就是矛盾. 第二, 生成脚本的实现是否忠实, 业务背景里写的那个分布, 那个占比, 那个业务陷阱, 代码里是不是真的这样生成的, 还是随手用了一个均匀分布敷衍过去.

查出冲突之后, review 不擅自替作者做决定. 冲突会被记录下来, 连同双方的证据一起交给人类判断, 到底该改业务背景去迁就代码, 还是改代码去兑现业务背景, 这是一个需要业务判断的合理化过程, 应该留给人, 而不是让 AI 自己拍板.

---

## 3. 两个 session, 不能自己审自己

review 不能让写数据集的那个 session 自己审自己. 自己审自己有一个结构性问题, 写出这份数据的那个上下文, 天然倾向于相信自己当初的判断是对的, 看不出自己的盲点. 所以这里必须拆成两个独立的 session, 一个只负责挑问题, 一个只负责照着问题改, 两者互不知情对方的思考过程, 靠输出的文件互相验证.

挑问题的 session 是只读的, 它只能 Read 四份 -cn 文件, 必要时跑 `sqlite3` 做实测验证, 但不能改任何一个数据集文件, 结论只写进它自己的 review 记录里. 改问题的 session 才有写权限, 它读 review 记录, 决定接受还是拒绝每一条意见, 动手改四份文件, 再跑一次生成脚本验证改动是否生效, 把这一轮做了什么写进它自己的 fix 记录里.

这个来回不是一轮就结束, 而是一个可以反复迭代的过程. 挑问题的 session 下一轮会重新读一遍被改过的文件, 确认上一轮的问题是不是真的被修复了, 有没有引入新问题, 这样滚动几轮, 数据集才会真正收敛到干净的状态. 传统上这也可以是人开两个终端手动来回念给对方听, 但这个项目选择相信 AI 的判断力, 把这个来回过程完全交给两个 AI session 自动跑.

---

## 4. 两个 session 怎么隔空对话

两个 session 互不知情对方的思考过程, 但又要能接力干活, 靠的是约定好的文件命名, 而不是把上一个 session 的输出文本硬塞进下一个 session 的 prompt 里. 具体是一套 `review-NN.md` 和 `fix-NN.md` 的编号文件, 写在数据集自己的目录下, `NN` 是两位数的轮次编号.

挑问题的 session 每一轮把详细意见写进 `review-{NN}.md`. 改问题的 session 读这份 `review-{NN}.md`, 决定接受哪些拒绝哪些, 动手改完之后, 把这一轮做了什么, 为什么拒绝某些意见, 验证结果如何, 写进 `fix-{NN}.md`. 下一轮挑问题的 session 开始之前, 会被告知上一轮的 `fix-{NN}.md` 在哪, 让它重新读一遍当前的四份文件再下判断, 而不是凭上一轮记在自己上下文里的旧印象. 如此往复, `review-01.md`, `fix-01.md`, `review-02.md`, `fix-02.md` 这样一路编号下去, 每一轮的问题和答复都完整落盘, 谁都能翻回去看某一轮到底发生了什么, 也能单独重放某一轮.

这套机制的具体实现细节, 包括每一轮 prompt 怎么写, 什么时候该重新 Read 文件, review 和 fix 各自的硬性约束, 都在 [.claude/skills/review-fake-data-generator/SKILL.md](../.claude/skills/review-fake-data-generator/SKILL.md) 和 [.claude/skills/fake-data-generator/SKILL.md](../.claude/skills/fake-data-generator/SKILL.md) 里定义, 以那里为准.
