# Kestrel Compute 训练集群自愈调度业务背景

本文档是这套数据集的业务底稿. 表结构请看 `02-cloud_provider_gpu_fleet_selfhealing_large_er_document-cn.md`, 具体查询请看 `03-cloud_provider_gpu_fleet_selfhealing_large_sql_queries-cn.md`.

这份数据集面向 Data Scientist, 不是面向 Data Analyst. 它的重点不是 "把业务算清楚", 而是 "把模型建起来并且不被自己骗到". 两者需要的数据结构差别很大, 第 6 节会专门讲这个差别.

---

## 1. 这家公司是谁

Kestrel Compute, Inc. 是一家总部位于俄亥俄州 Columbus 的 AI 算力运营商, 在美国四个州运营 6 座园区, 签约电力容量 420 MW, 部署约 180,000 张 GPU. 公司靠出租 GPU 小时赚钱, 客户是一批做基础模型的实验室, 药企研发团队和自动驾驶公司.

这份数据集来自公司里一个叫 ML Platform and Fleet Reliability 的团队, 负责人是 Director of ML Platform Ana Reyes, 团队 9 个人, 向 CTO Priya Nair 汇报. 数据覆盖的范围很窄但很深: Abilene 园区的 Cluster A3 这一个训练集群, 200 个节点, 每节点 8 张卡合计 1,600 张 GPU, 时间窗是 2026 年 2 月 1 日到 5 月 31 日整整 120 天.

之所以只取一个集群, 是因为要建的模型是节点粒度的, 而节点粒度的遥测数据量极大. 一个集群 120 天已经是 215 万行遥测. 模型在 A3 上验证成功之后会推到全部 6 座园区, 但那是下一阶段的事.

如果你读过 `utilities_datacenter_power_procurement_demand_response_high` 那份数据集, 这是同一家公司. 那边讲能源团队怎么买电和参与需求响应, 这边讲算力团队怎么防止作业被硬件故障打断. 两边有一个显式的接口: 那边园区参与需求响应主动削减负载时, 这边就表现为一种中断原因, 在 `job_interruption.cause` 里叫 `DR_CURTAILMENT`.

---

## 2. 要解决的问题

Cluster A3 上跑的大多是长周期预训练. 一个 1,024 卡的任务连续跑三到五周是常态. 这类任务对硬件故障极其脆弱.

事情通常是这样发生的. 某个节点的 HBM 出现不可纠正错误, 整个分布式作业当场崩溃. 系统回滚到上一个 checkpoint, 而预训练的 checkpoint 间隔是 240 分钟, 平均要白算两个小时. 加上重新排队和恢复到满速的时间, 一次中断的完整代价常常是四到六个小时乘以上千张卡.

FY2026 前四个月, Cluster A3 一共发生 978 次作业中断, 其中 814 次的直接原因是节点硬件故障. 累计损失 217 万 GPU 小时, 按内部成本 2.85 美元每 GPU 小时折算, 618 万美元.

问题的关键不在于故障率高不高, 而在于**运维是事后反应的**. 健康监控系统会在节点挂掉的那一刻发告警, 但那时候作业已经崩了, 损失已经发生. 团队真正想要的是提前几个小时知道哪个节点要出事, 趁两次 checkpoint 之间的空档把那部分 shard 迁走, 让作业几乎无感.

这件事过去做不到, 不是因为没人想到. 是因为三个缺口同时存在.

第一, 没有一个可信的 "这个节点未来 24 小时会挂" 的**概率**. 有的只是阈值告警, 而阈值告警要么太吵 (设低了, 每天几十条, 运维直接忽略) 要么太晚 (设高了, 报出来的时候已经在崩溃边缘).

第二, 就算有了概率, 也不知道**现在迁移划算还是赌它撑到作业结束划算**. 一个 24 小时故障概率 40% 的节点, 如果上面的作业两小时后就跑完了, 动它就是白花钱. 这个判断需要同时知道作业还要跑多久, 以及真中断一次要付多少代价.

第三, 决策必须在几秒内完成, 而且一天要做几百次, 人根本来不及介入.

这三个缺口至少对应三个模型: M1 补上概率, M2 与 M3 一起补上 "现在动还是赌它撑到底" 的决策依据. 再加上 M4 排队等待时长与 M5 慢节点检测, 就构成了一个**模型族**. 这就是为什么这个项目从一开始就不是 "训一个故障预测模型".

## 3. 你在这里做什么

你是刚加入 ML Platform 团队的 Data Scientist, 直接向 Ana Reyes 汇报.

模型族的第一个版本已经在 2026 年 4 月 1 日上线了, 由上一位 DS 建的, 他在五月初离职. 你接手的时候面对的是这样一个局面: 系统在跑, 每天在做决策, 但没有人能说清楚它到底赚了多少钱, 也没有人敢动它, 因为不知道改动会不会让它变差.

Ana 给你的任务有三件. 第一, 把上线两个月的真实收益算出来, 这个数字要进季度评审. 第二, 诊断模型有没有退化, 如果有, 找出原因. 第三, 出一个 v2 的重训方案.

时间上, 季度评审在六月中旬, 数据快照截止到 5 月 31 日, 也就是这份数据集里的 `REFERENCE_DATE`.

有一件事需要你特别小心. 上一位 DS 留下的训练记录里, 有两次实验的指标好得不真实: `training_run` 表里 test AUC 冲到 0.94 的那一行 (TR-M1-002), 以及按随机而非时间切分把 AUC 虚高到 0.92 的那一行 (TR-M1-003). 你需要判断那些指标是真的还是方法论出了问题, 因为 v2 方案要不要沿用他的特征集, 完全取决于这个判断.

## 4. 模型族与决策规则

### 五个模型

| 编号 | 模型 | 任务类型 | 输出 | 在闭环里的作用 |
| :-- | :--- | :--- | :--- | :--- |
| M1 | 节点故障风险 | 二分类 | 未来 24 小时故障概率 | 决定要不要考虑动这个节点 |
| M2 | 作业剩余时长 | 分位数回归 | 剩余时间的 P10 / P50 / P90 | 决定风险窗口该取多长 |
| M3 | 中断恢复时长 | 回归 | 从中断到恢复满速的分钟数 | 中断代价公式的关键输入 |
| M4 | 排队等待时长 | 分位数回归 | 新作业拿到资源前的等待时间 | 迁移目标节点的可得性 |
| M5 | 慢节点检测 | 无监督 | 性能劣化但未故障的节点 | 提前发现亚健康节点 |

### 决策规则

模型不直接做决定. 决定来自一个显式的期望效用比较:

```
迁移收益 = P_fail(节点, 风险窗口) x 中断代价
中断代价 = 受影响 GPU 数 x (checkpoint 回滚时长 + M3 恢复时长) x GPU 小时成本
迁移成本 = 受影响 GPU 数 x 迁移耗时 x GPU 小时成本 + 备用节点占用成本

若 迁移收益 > 迁移成本 则现在迁移, 否则继续观察
```

这个式子解释了两件容易被忽略的事.

**为什么 M2 必须输出分布而不是点估计.** 风险窗口取多长, 取决于作业还要跑多久. 如果 M2 说 "还有 2 小时" 但实际还有 20 小时, 决策就完全错了. 用 P90 而不是 P50 做风险窗口, 是因为决策的代价是不对称的: 低估作业时长会让你放过一个该迁的节点, 代价是几万美元; 高估只会让你多迁一次, 代价是几百美元.

**为什么 M1 必须校准.** 式子里的 `P_fail` 是要拿去乘美元的. 排序对了但数值不对, 整个决策就错了. 一个 AUC 0.85 但系统性把概率高估十倍的模型, 会让你把所有钱花在不该迁的节点上. 这套数据集里的生产模型恰好就是未校准的, 第 5 节陷阱 8 有实测数字.

## 5. 数据覆盖了什么

时间窗 120 天, 从 2026-02-01 到 2026-05-31. 中间有一条关键的分界线: **2026-04-01 模型上线**. 分界线前 59 天没有任何模型干预, 故障该发生就发生, 标签是干净的. 分界线后 61 天模型在线并且真的在改变世界, 标签因此被自己的行动污染. 这条分界线是这份数据集最重要的结构.

规模上: 200 个节点, 1,600 张 GPU (其中 28 张已 RMA 退回), 900 个作业, 1,729 次作业尝试, 978 次中断, 125 张维修工单. 遥测 15 分钟粒度共 215 万行, 特征与标签每 6 小时一个 as_of 点共 88,828 行. 全库 26 张表, 合计约 257 万行.

标签的正例率是 0.33%, 也就是 88,828 个样本里有 293 个正例. 分时段看差别很大:

| 切分 | 样本数 | 正例数 | 正例率 |
| :--- | :-- | :-- | :-- |
| train (2/1 到 3/12) | 24,028 | 106 | 0.441% |
| validation (3/12 到 3/22) | 8,000 | 77 | 0.963% |
| test (3/22 到 4/1) | 8,000 | 50 | 0.625% |
| production (4/1 之后) | 48,800 | 60 | 0.123% |

production 段的正例率只有前面的四分之一到六分之一. 这不是因为硬件突然变好了, 是因为模型把一部分故障拦掉了. 理解这一行是理解整份数据集的钥匙.

几个刻意的取舍. 第一, GB200 批次节点在 2026 年 2 月底才上架, 占机队四分之一, 训练窗前段几乎没有它的样本. 第二, 快照时刻仍在运行的作业没有真实结束时间, 这是真实的右删失而不是缺失值. 第三, 已 RMA 退回的 GPU 从 `gpu_device` 主表移除, 只留在工单里.

## 6. 为什么这份数据集有四层

这是它和典型分析型数据集最根本的差别. 分析型数据集只需要事实层, 因为分析师要回答的是 "过去发生了什么". 建模需要四层, 因为你要回答的是 "在过去的某个时刻, 只用当时能看到的信息, 能不能预测接下来会发生什么".

**第一层 原始事实.** 遥测, 硬件事件, 作业, 工单, 状态机. 全部只追加, 每行带 `event_time` 和 `ingest_time` 两个时间, 从不原地修改.

**第二层 特征与标签.** `feature_snapshot` 以 (节点, as_of_ts) 为键, 存的不是 "当前状态", 而是 "截至 as_of 那一刻可见的状态". `label_record` 同样以 as_of 为键, 额外带一个 `label_known_at`, 表示这个标签到什么时候才真正可知. 配套的 `feature_definition` 是特征字典, 每个特征带 `availability_lag_minutes`, 表示线上打分时这个特征相对当前时刻滞后多久可得.

**第三层 模型与预测.** `model_registry` 登记模型版本, `training_run` 记录每次训练用了哪个切分与哪些特征, `prediction_log` 记录线上每一次打分. 有了打分日志才能做回溯评估和漂移监控.

**第四层 决策与结果.** `decision_log` 同时记录模型建议了什么和实际执行了什么 (两者会不一致), `action_outcome` 记录结果. 这两张表是算真实收益和做因果评估的唯一依据.

### 留出组, 这份数据集最重要的设计

`decision_log` 里有一个 `is_holdout` 字段. 18% 的劣化事件被随机分进留出臂, 模型建议排空但**刻意不执行**, 放节点自然运行到底.

这看起来是在故意亏钱, 事实上也确实在亏钱. 但没有它, 模型上线之后就再也拿不到干净标签了: 凡是被判高风险的节点都被提前修好了, 于是它们永远不会 "故障", 数据会告诉你高风险特征不再预示故障. 拿这样的数据重训, 模型会一轮比一轮差.

留出组是唯一的无偏标签来源, 是真实 ML 团队必须付的代价. 需要注意的是, 因为人工 override 而没被执行的那些样本 (`override_reason` 非空) **不能** 当无偏样本用: override 的理由通常是 "这个节点上跑着关键客户的作业", 这与节点本身的风险相关, 属于非随机选择.

## 7. 十个建模陷阱

这份数据集的价值不在于数据本身, 而在于它把十个真实的建模陷阱做进了数据结构里. 下面每一条都给出了实测数字, 数字是真的跑模型测出来的, 不是编的.

**1. 选择性标签.** 上线前正例率 0.582%, 上线后掉到 0.123%. 拿上线后的全量数据重训, 模型在 5 月下旬的 AUC 是 0.5688; 剔除 `is_label_censored = 1` 的样本再重训, AUC 回到 0.6562. 这是整份数据集的王牌陷阱.

**2. 特征泄漏.** `ops_attention_flag` 与 `pending_drain_flag` 两个特征的计算窗口写成了前向 18 小时. 加上它们, test AUC 从 0.8513 跳到 0.9438. 这两列在 `feature_definition` 里的 `availability_lag_minutes` 是 -1080, 负数就是线索.

**3. 时间泄漏.** 同一节点相邻 as_of 点高度自相关, 而且每个节点有可辨认的固定偏移 (温度基线, 风扇转速基线). 随机划分 AUC 0.9209, 按时间划分 0.8513, 虚高 7 个百分点.

**4. 训练服务偏斜.** 三个特征 (`hbm_temp_excess_over_lot`, `firmware_age_days`, `open_work_order_count`) 的 `availability_lag_minutes` 是 60, 线上只能拿到一小时前的值. `prediction_log.feature_as_of_ts` 记录了线上真正取到的特征时点, 比 `as_of_ts` 早 60 分钟. 训练时按 `as_of_ts` join 会拿到线上根本拿不到的信息.

**5. 标签迟到.** `label_known_at` 平均比 `as_of_ts` 晚 26 小时 (24 小时观测窗加 2 小时运维定性). 用 as_of 时刻还不可知的标签训练那个时刻的模型, 是最隐蔽的错误之一.

**6. 分布漂移.** 三个采购批次的劣化机理不同: H100 与 H200 是热失效主导, GB200 是互联与供电失效主导. 用训练窗数据训出的模型在上线后各批次的 AUC 是 H100 0.9016, H200 0.8274, GB200 0.8207.

**7. 极端不平衡.** 正例率 0.33%. 用 accuracy 评估毫无意义 (全预测负例就有 99.67%). 而且最优阈值取决于中断代价与迁移代价之比, 不是 0.5, 也不是各批次统一.

**8. 概率未校准.** 生产模型的分数经过一个未校准的变换. `calibration_bin` 里, 预测值落在 0.8 到 0.9 那一箱的样本, 预测均值 0.848, 真实频率只有 0.0625, 高估了十三倍. 拿这个概率去乘美元, 决策必然全错.

**9. 右删失.** 900 个作业里 225 个在快照时刻仍在运行, 没有 `actual_hours`. 这 225 个的 `planned_hours` 平均是 553.9 小时, 而已完成的 675 个平均只有 127.0 小时. 直接丢弃删失样本, 会把长作业系统性地从训练集里剔掉, 而长作业恰恰是迁移决策最关键的那一批.

**10. 幸存者偏差.** 原始安装 1,600 张卡, `gpu_device` 表里只剩 1,572 张, 28 张已 RMA 退回并从主表移除, 只在 `maintenance_work_order.replaced_serial` 里留有记录. 直接用在库设备算 MTBF 会系统性高估可靠性.

## 8. 持续追加下模型仍然可用

这份数据集是一个截止到 2026-05-31 的快照. 但它的结构设计保证, 把它接上真实的数据流之后, 上面所有的训练, 评估, 打分, 决策逻辑一行都不用改.

**全部只追加, 从不更新.** 每张事实表有 `event_time` 与 `ingest_time` 两列. 新数据到来就是新行, 历史行永远不变, 因此任何时点的重放都能得到当时的视图.

**特征与标签以 as_of 为键.** `feature_snapshot` 与 `label_record` 不是当前状态而是 "截至某时刻的状态". 追加新数据只是增加新的 as_of 行, 已有行不受影响. 这让回溯训练与线上推理走完全相同的代码路径, 也是消除训练服务偏斜的根本办法.

**切分边界是数据不是代码.** `dataset_split` 把 train / validation / test / production 的时间边界存成行, 带版本号. 窗口往前滚动时改的是这张表, 不是训练脚本. `training_run.split_version` 绑定了每次训练用的是哪个版本的切分, 因此任何一次历史训练都可复现.

## 9. 术语表

| 术语 | 一句话解释 | 在这里为什么重要 |
| :--- | :--- | :--- |
| as_of | 特征与标签所对应的 "站在那一刻往回看" 的时点 | 整个第二层的主键之一, 没有它就没有 point-in-time 正确性 |
| Point-in-time correctness | 只用某时刻真实可见的信息构造特征 | 违反它就是泄漏, 离线指标会好到不真实 |
| Availability lag | 某个特征在线上相对当前时刻滞后多久可得 | 为负说明取用了未来信息, 为正说明训练时不能用理想值 |
| Label horizon | 标签的观测窗长度, 这里是 24 小时 | 决定了预测提前量, 也决定了正例的稀疏程度 |
| Label known at | 标签真正可知的时刻 | 比 as_of 晚 26 小时, 用早于它的模型去用这个标签就是穿越 |
| Selective labels | 模型的行动阻止了结果发生, 导致标签不可观测 | 上线后最主要的数据质量问题, 本数据集的王牌陷阱 |
| Holdout arm | 刻意不执行模型建议的随机留出组 | 上线后唯一的无偏标签来源 |
| Censoring | 结局不可观测. 右删失指 "还没结束" | 作业时长与故障标签两处都有 |
| Calibration | 预测概率与真实频率是否一致 | 决策公式要拿概率乘美元, 不校准就没法用 |
| Brier score | 概率预测的均方误差, 越小越好 | 同时衡量区分度与校准度, 比 AUC 更贴近决策价值 |
| PR-AUC | 精确率召回率曲线下面积 | 极端不平衡下比 ROC-AUC 更有信息量 |
| Distribution drift | 线上数据分布偏离训练分布 | 这里由新硬件批次的不同失效机理造成 |
| Train-serve skew | 训练时用的特征与线上服务时不一致 | 由 availability lag 被忽略造成 |
| XID error | NVIDIA 驱动报告的 GPU 硬件错误码 | 故障前最强的单点信号, 但太稀疏, 单靠它做规则来不及 |
| ECC | 显存纠错码. 可纠正错误上升是劣化的早期信号 | M1 最重要的特征族之一 |
| HBM | 高带宽显存. 温度是热失效的主要观测量 | H100 与 H200 批次的主导失效机理 |
| NVLink retransmit | GPU 间互联的重传率 | GB200 批次的主导失效机理 |
| Checkpoint | 训练任务把中间状态写到存储的动作 | 间隔越长, 中断时回滚损失越大 |
| Goodput | 真正产出有效计算的比例 | 被中断和回滚吃掉的部分不算 |
| MFU | Model FLOPs Utilization, 算力有效利用率 | 慢节点检测 (M5) 的主要观测量 |
| Straggler | 拖慢整个同步组的慢节点 | 未故障但已劣化, 无标签, 需要无监督方法 |

## 10. 关键指标与口径

**故障标签 (M1 的 y)**

```
label_value = 1  当且仅当  节点在 (as_of, as_of + 24h] 内进入 DOWN 状态
且 reason = 'UNPLANNED_HARDWARE_FAILURE'
label_known_at = as_of + 24h + 2h
```

`label_definition` 表里还有另外两个未物化的口径 (72 小时窗, 以及 "故障时该节点上有作业在跑"), 需要自己用 SQL 重算. 三个口径训出来是三个不同的模型, 业务含义也不同.

**决策净收益**

```
net_benefit_usd = counterfactual_lost_usd - actual_lost_usd - migration_cost_usd
```

`counterfactual_lost_usd` 是 "如果不采取行动会损失多少" 的估计. 注意这是一个估计而不是观测值, 只有留出组能提供接近观测的反事实.

**中断代价**

```
lost_gpu_hours = gpus_allocated x (rollback_minutes + requeue_wait_minutes + recovery_minutes) / 60
lost_usd       = lost_gpu_hours x 2.85
```

三项时长里, `rollback_minutes` 由 checkpoint 间隔决定, `recovery_minutes` 是 M3 要预测的量.

**评估指标的取舍**

极端不平衡下, ROC-AUC 会被大量容易的负例稀释, 看起来总是不错. 建议主看 PR-AUC 与固定预算下的召回率 (比如 "每天只允许处理分数最高的 1.5% 节点, 这个预算下能抓住多少故障"). Brier score 用来单独盯校准.

**漂移监控**

```
按 purchase_lot 切片, 分别计算 AUC 与 Brier
任一切片的 AUC 相对训练期下降超过 5 个百分点, 触发重训评估
```

`evaluation_metric` 表已经按 `slice_dimension` 存了切片指标, 直接查即可.
