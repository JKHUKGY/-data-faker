## 2. 商业模式:NovaRisk 怎么赚钱

NovaRisk 是一家 **B2B SaaS** 公司。它的客户**不是**消费者,而是银行、信用合作社、fintech、BNPL 借贷方、支付处理商。换句话说,普通人永远不会知道 NovaRisk 的存在 — 他们只在自己银行 APP 里看到"转账完成"或"我们需要验证一下你的身份"。

每个客户与 NovaRisk 签**多年期合同**,年合同金额 (ACV) 约 **24 万 – 120 万美元** (落在 `client_institution.annual_contract_value_usd` 字段里),按订阅 + 用量混合计费。作为回报,客户拿到一整套平台能力:

1. **实时打分 API** — 客户 POST 一笔交易,NovaRisk 在 100 毫秒内 POST 回一个 0–999 的风险分数加一个建议动作。
2. **模型市场** — NovaRisk 训练的 ML 模型,既有**无监督**类型 (不需要欺诈标签,通过聚类异常行为发现协同攻击团伙),也有**有监督**类型 (用确认过的欺诈标签训练)。
3. **规则引擎** — 分析师可以手写硬规则,例如"拒绝任何 > $10K、设备使用不到 24 小时、转向高风险国家的电汇"。
4. **案件管理工作台** — 分析师分流告警、打包成案件、提交 SAR。
5. **对话式 AI 代理 (代号 "Vera")** — 分析师用自然语言提问 ("给我看昨天所有 $5K 以上来自新设备的交易"),无需写 SQL 或配规则。
6. **数据联盟 (Data Consortium)** — 跨 NovaRisk 全体客户共享的脱敏欺诈信号:某个设备指纹在 A 银行被抓到欺诈,B 银行下次见到它时也会被预警。

**银行为什么买,而不是自己建?**

- 一家典型中型银行没有 500 名 ML 工程师和图异常研究团队。
- 银行的反欺诈团队通常是 40 人,不是 4000 人 — 他们需要力量倍增器。
- 节省可量化:人工写一份 SAR 以前要分析师花约 **21 小时**,用 Vera 起草初稿后只要约 **2 小时**。一年几千份 SAR,光人力节省就足以覆盖合同费用。

这就是为什么 `sar_report.ai_drafted = TRUE` 的每一行都重要 — 它是可计费价值的直接证据。

**单位经济学速记 (数量级):** 软件毛利率高 (典型 SaaS 75%–85% 区间),最大的可变成本是 Vera 背后的 LLM 推理算力。这也是 CFO 要把 token 成本分摊到具体 AI 子代理和工具上的原因 (见业务问题 Q8)。

## 3. 行业概览:实时反欺诈 & AML 这个市场在做什么

如果你来自别的行业,这一节让你能跟人聊起这个市场。

**这个行业到底解决什么问题?** 每次有人刷卡、发 Zelle 转账、在线开银行账户、或发起 BNPL (先买后付) 结账,**总有某个银行或 fintech 必须在一秒内做出 yes/no 判断**:这是不是真实客户在做真实的事?还是有人想偷钱或洗黑钱?

这个判断难在三点:

- **好人流量极大。** 仅美国每天就有数十亿笔支付,客户期待秒级批准。慢一点、错拒一笔,客户体验就受伤。
- **坏人藏在好人里。** 大约 **每 1000 笔交易里有 1 笔是欺诈**,这 0.1% 一旦漏过,能把一家小银行一年的利润抹平。
- **监管悬在头上。** 监管要求银行每发现一笔疑似洗钱就上报一份文书 (SAR),并在客户开户时做身份识别 (KYC) 检查。出问题罚款可能上亿美元。

**主要玩家类别** (不点真实公司名):

- **AI 原生反欺诈 SaaS 厂商** — 像 NovaRisk 这样,主打无监督/图机器学习,卖实时打分 + 案件管理。
- **传统规则引擎厂商** — 老牌反欺诈系统,以人工规则为主,正在被 AI 原生玩家蚕食。
- **银行自建团队** — 大型银行有自己的风控部门,但大多数中型机构买而非建。
- **支付网络与处理商** — 卡组织和处理商自带一层风控,与第三方 SaaS 互补。

**相关监管机构与合规框架** (北美为主):

| 机构 / 框架 | 是什么 |
|---|---|
| **FinCEN** | 美国金融犯罪执法局,SAR 的接收方 |
| **OFAC** | 美国海外资产控制办公室,维护制裁名单 (SDN List) |
| **FINTRAC** | 加拿大金融交易和报告分析中心 (加拿大版 FinCEN) |
| **BSA / AML** | 银行保密法 / 反洗钱法规,要求银行监控并上报可疑活动 |
| **KYC / CDD** | 开户时的客户身份识别与尽职调查要求 |
| **FATF** | 反洗钱金融行动特别工作组,制定国际反洗钱标准 |
| **FCA / EU AMLR** | 英国金融行为监管局 / 2027 年起生效的欧盟反洗钱条例 (服务跨境客户时相关) |

**当下塑造这个市场的宏观力量:**

- **AI 攻防升级。** 攻击者用偷来的身份、AI 生成的 deepfake、偷来的设备指纹、钱骡账户、"structuring" 拆单等手段,且彼此快速分享套路。防守方必须同样用 AI 才跟得上。
- **监管收紧。** 全球反洗钱条例越来越严,SAR 上报量逐年上升,人工成本难以为继 — 这正是 AI 起草 SAR 的商业窗口。
- **共享情报。** 单家银行只能看到自己的流量,而欺诈团伙跨机构作案 — 数据联盟 (consortium) 成为关键护城河。

## 7. 行业知识科普:看懂数据前需要的 30 分钟背景

### 7.1 "实时打分"到底怎么发生

客户在银行 APP 里按下"发送 $500"时,银行后端暂停约 80 毫秒,问 NovaRisk 的 API:*"客户 12345,设备指纹 abc…,凌晨 2 点把 $500 从支票账户转到拉各斯的对手方 — 风险评分?"* NovaRisk 返回一个 **0 到 999 的数字**加一个**建议动作**。银行 APP 然后要么放行、要么要求刷脸、要么阻断。整个过程客户看不到 NovaRisk。

### 7.2 分数怎么映射到决策

打分引擎输出 0–999,再按固定阈值切成四种动作:

| 分数区间 | 决策 | 银行 UI 做什么 |
|---|---|---|
| < 400 | **APPROVE** | 直接放行 |
| 400 – 599 | **STEP_UP** | 要求额外验证 (刷脸 / 短信码) |
| 600 – 799 | **REVIEW** | 暂挂,转人工审查 |
| ≥ 800 | **DECLINE** | 直接拦截 |

**告警阈值是 600** — 即只要最终分数进入 REVIEW 段 (或触发了某条启用规则),就生成一条告警。

### 7.3 从一笔交易到一份监管申报:数据的生命线

这个数据集不是几张孤立的表,而是 12 家客户在一个季度里**完整业务活动的数据轨迹**:

```
签合同 (client_institution) → 银行给客户开户 (end_user, 跑 KYC)
   → 客户开账户 (account) → 客户登录产生 session (device_session)
   → 按"发送" 产生交易 (transaction)
   → 打分引擎 <100ms 返回 (risk_score_event)
   → 分数 ≥ 600 或规则触发 → 告警 (alert)
   → 分析师把若干告警打包 → 调查案件 (investigation_case)
   → 确认洗钱 → 向 FinCEN 提交 SAR (sar_report)
   → 分析师全程与 AI 代理 Vera 对话 (agent_interaction_log)
```

隐含的时间箭头从左到右:一笔交易的时间必然晚于账户开户,后者晚于用户开户,后者晚于客户签约。生成器严格执行这个时序,因此数据读起来像真实历史,而不是随机散落的行。

### 7.4 告警与案件的生命周期

- **告警 (alert)** 大多从 `OPEN` 开始,被分流到 `IN_REVIEW`,然后关闭为误报 (`CLOSED_FALSE_POSITIVE`) 或确认欺诈 (`CLOSED_CONFIRMED_FRAUD`),或升级 (`ESCALATED`) 成案件。**只有 `ESCALATED` 和 `CLOSED_CONFIRMED_FRAUD` 状态的告警才会被打包进案件** — 大多数告警永远不会变成案件,这才符合现实。
- **案件 (investigation_case)** 从 `OPEN` 走到 `SAR_FILED` (提交了监管申报) 或 `CLOSED_NO_ACTION` (查无实据关闭)。

### 7.5 反洗钱的几个核心套路

- **Structuring (拆单):** 把一笔大额 (比如 $3 万) 拆成多笔刚好低于 $1 万上报门槛的存款,以躲避自动上报。是 SAR 里最常见的叙述模式之一。
- **Mule account (钱骡账户):** 有意或无意被用来中转洗钱资金的账户,通常"进一笔、立刻出一笔"。
- **Account takeover (账户盗用):** 合法账户被攻击者劫持。常见信号是 VPN + 地理位置与登记国家不符。
- **Deepfake onboarding:** 用 AI 生成的假身份骗过开户时的 KYC 人脸/证件核验。

### 7.6 模型怎么上线:冠军 vs 挑战者

每个客户同一时刻部署两个模型:一个**冠军 (champion)** 在生产中处理约 85% 流量,一个**挑战者 (challenger)** 镜像约 15% 流量做 A/B 测试。MLOps 团队比较两者的 decline 率;差距足够小,才把挑战者推成新冠军。

### 7.7 为什么共享设备是红旗

每台设备有一个**指纹 (fingerprint)** — 浏览器版本、字体、屏幕尺寸、操作系统等信号的哈希。如果同一台物理设备被十个号称"互不相关"的账户共用,这往往是有组织欺诈团伙的典型特征。若这台设备还**横跨多家银行**,信号更强 — 而这正是数据联盟 (Data Consortium) 的价值所在。

| **BSA** (Bank Secrecy Act) | 银行保密法,AML 监管的法律基础 | 解释银行为什么必须监控并上报 |
| **FATF / FINTRAC** | 国际反洗钱标准组织 / 加拿大版 FinCEN | 跨境与加拿大客户的合规背景 |
| **ACH** | 美国自动清算系统,银行间批量转账网络 | `transaction_type` 里的 `ach_push` / `ach_pull` |
| **Wire** | 电汇,实时大额跨行/跨境转账 | 高风险交易类型,告警占比高 |
| **BNPL** (Buy-Now-Pay-Later) | 先买后付,一种消费分期 | 客户类型之一 (OneTap BNPL) |
| **Structuring** | 拆单,把大额拆成多笔低于上报门槛 | Q20 在 SAR 叙述里搜这个词 |
| **Mule account** | 钱骡账户,中转洗钱资金的账户 | 一种欺诈类型 (`mule_account`) |
| **Account takeover** | 账户盗用,合法账户被劫持 | 欺诈类型之一,VPN+地理不符是信号 |
| **Card-not-present** | 无卡支付欺诈,盗用卡号在线消费 | card_purchase 的主要欺诈类型 |
| **Deepfake onboarding** | 用 AI 假身份骗过 KYC | 最高 severity 的欺诈类型 |
| **Device fingerprint** | 设备指纹,由设备信号算出的唯一哈希 | 协同团伙检测的核心 (Q7) |
| **Emulator** | 模拟器,非真实物理设备,常用于批量欺诈 | `device.is_emulator`,红旗信号 |
| **Champion / Challenger** | 冠军模型 (生产) / 挑战者模型 (A/B 测试) | `ml_model.is_champion`;Q14 比较两者 |
| **A/B test** | 把一部分流量分给新方案做对照实验 | 约 15% 流量走挑战者模型 |
| **False Positive (FP) / True Positive (TP)** | 误报 (其实没问题却被告警) / 真阳 (确实是欺诈) | `is_true_positive`;Q5 算规则误报率 |
| **SLA** (Service Level Agreement) | 服务等级承诺,这里指 <100ms p99 延迟 | Q1 检查打分 API 是否达标 |
| **p50 / p95 / p99** | 中位数 / 第 95 / 第 99 百分位延迟 | 衡量"绝大多数请求"有多快 |
| **Latency** | 延迟,API 一来一回的毫秒数 | `latency_ms` 字段 |
| **ARR / ACV** | 年经常性收入 / 年合同金额 | 收入集中度分析的基础 (Q2、Q19) |
| **Data Consortium** | 数据联盟,跨客户共享的脱敏欺诈信号 | 跨机构团伙检测的护城河 |
| **Step-up auth** | 升级验证,要求额外身份核验 | STEP_UP 决策对应的动作 |
| **High-risk corridor** | 高风险走廊,流向受制裁/高风险国家的资金通道 | `is_high_risk_corridor`;Q8 |
| **top_feature / Explainability** | 贡献最大的特征 / 模型可解释性输出 | `risk_score_event.top_feature` |

## 9. 关键指标与公式

下面是出现在 SQL 查询里或读者需要知道的指标。记号用大白话伪代码,够用即可。

**SLA 延迟百分位 (Q1)**
```
p99_latency = 把所有 latency_ms 升序排列后, 第 99% 位置的那个值
pct_over_100ms_sla = COUNT(latency_ms > 100) / COUNT(*)
-- 绿灯条件: 生产环境 p99 ≤ 100ms
```

**规则误报率 (Q5)**
```
fp_rate = false_positives / (false_positives + true_positives)
-- 只统计已判定 (is_true_positive IS NOT NULL) 的告警
-- 故意排除纯 ML 告警 (detection_rule_id IS NULL), 因为问题是"该退役哪条规则"
```

**每千笔交易确认欺诈数 (Q11)**
```
confirmed_fraud_per_1k_txn = SUM(确认欺诈告警数) / SUM(交易数) * 1000
-- 按 customer_risk_rating (LOW/MEDIUM/HIGH) 分组
-- 理想情况下应随 LOW → MEDIUM → HIGH 单调上升
```

**冠军 vs 挑战者 decline 率差 (Q14)**
```
decline_rate = COUNT(decision = 'DECLINE') / COUNT(*)   -- 注意用率, 不用绝对数 (流量份额不同)
decline_rate_gap = challenger_decline_rate - champion_decline_rate
-- 正值 = 挑战者更保守; 负值 = 更宽松; |gap| 小才安全推前
```

**收入集中度 (Q2、Q19)**
```
pct_of_total_arr  = client_ACV / SUM(所有 active 客户的 ACV)
cumulative_pct    = 按 ACV 降序累加的 ACV / total_ARR
-- top-3 累计份额是衡量集中度风险的关键 (本数据集约 41%)
```

**每日告警率 (Q9)**
```
alert_rate = COUNT(DISTINCT 当日告警) / COUNT(DISTINCT 当日交易)
```

**高风险走廊敞口 (Q8)**
```
high_risk_exposure_usd = SUM(amount_usd) WHERE is_high_risk_corridor = 1   -- 按客户分组
```

**真正 7 自然日滚动告警 (Q16)**
```
rolling_7d_alerts = 当前日往前数 7 个"自然日"的告警数之和 (含 0 告警的安静日)
-- 必须用日历 cross join 补 0, 否则会把安静日跳过, 掩盖趋势归零
```

**分析师平均关案时长 (Q6)**
```
avg_hours_to_close = AVG( (closed_at - opened_at) 的小时数 ) WHERE closed_at IS NOT NULL
```

**AI 代理成本与接受率 (Q13)**
```
total_tokens   = SUM(tokens_used)                          -- 按 agent_name + tool_called 分组
approval_rate  = AVG(human_approved)                       -- 全场约 92%
```

**SAR AI 起草占比**
```
ai_drafted_share = COUNT(ai_drafted = TRUE) / COUNT(*)     -- 约 80%, NovaRisk 自动起草产品的产能证据
```
