## Stage 3. SQL 查询文档评审

### 教学质量
- 全部 20 个查询都完整具备五段式结构;角色标签与 Stage 1 的组织架构表完全一致。
- 解题思路普遍讲清楚了"为什么"而不只是复述 SQL(如 Query 3 对混杂变量的解释、Query 4 对反连接写法的必要性说明、Query 11 对 RANK 与 ROW_NUMBER 取舍的说明)。
- 期望结果说明都给出了具体的下一步行动建议。

### 业务逻辑问题
- Query 5(保底金额达成进度追踪)和 Query 20(续约优先级综合评分):都没有把"合同太新、还没到第一次报告周期"的情形排除在外。一份刚签约的活跃合同会因为时间过短而算出 `pacing_ratio ≈ 0`,在查询结果里和真正表现不佳的合同混在一起,无法区分。Stage 4 已确认:被 Query 5 标记的 26 份合同里,有 5 份(19%)其实一份版税报告都还没提交过。
- Query 20 的 `audit_health_quartile` 把零报告记录的合同当作"完全合规"(`COALESCE(..., 0)`),而同一份合同的 `mg_pacing_quartile` 却把同样的零报告状态当作最差的达成进度——对刚签约的新合同来说,这个综合评分内部自相矛盾。

### SQL 正确性问题
- 🟠 P1 — Query 12(第 488 行):解题思路声称"SQLite 不支持在 GROUP BY 里直接引用 SELECT 里定义的别名"——经直接测试证明这个说法是错的(`SELECT a+b AS x, COUNT(*) FROM t GROUP BY x` 在 SQLite 里能正确分组运行)。WHERE 子句确实有这个限制,文档对这部分的解释是对的;但把同样的限制归到 GROUP BY 头上是错误的。由于查询本身把完整表达式重复写了一遍,SQL 依然能正确运行,所以这属于教学准确性问题,不是功能性 bug。
- 未发现行数膨胀 / 重复计数类 bug——所有对 `license_agreement_channel` 的 LEFT JOIN 都因为该表的 UNIQUE 约束而是安全的;Query 3 里同一个 SKU 参与多个首播事件窗口的设计是刻意为之的正确方法论,不是 bug。
- `REFERENCE_DATE` 全程以字面量 `'2026-06-30'` 使用,未发现 `DATE('now')` 的用法。
- 未发现保留字未加引号的问题。

### 跨查询一致性
未发现指标定义漂移。`variance_pct` 始终直接读取预先算好的列;`pacing_ratio` 公式在 Query 5 和 Query 20 中完全一致(包括共同存在的新合同边界情形)。

## 总体结论

这是一份扎实、内部自洽的数据集。四个已记录的业务陷阱(版税低报、越权铺货、热度滞后、保底金额达成)在实测 SQLite 数据库中都精确复现了文档声称的量级;外键完整性和时序约束全部完美;生成器满足全部硬性规则要求;性能远优于目标。今天就可以直接用于演示、教学和 SQL 练习。

发现的问题集中在文档精确度层面,而非数据正确性:Q1 缺一条陷阱记录、两处公式笔误、一个 SQL 教学文档里的错误技术断言,外加几个 P2 级别的一致性小问题。唯一有轻微分析层面影响的是 Query 5/20 把"合同太新"和"真正表现不佳"混为一谈的问题,已列入修复清单(中等规模)。没有问题达到 P0 级别。最值得优先修复的一项,是把 Q1 的陷阱量级补充进文档——这是当前唯一一个还缺少 ER 文档陷阱记录的 marquee 业务问题。
